## なぜ足すのか

0004 の事後の確認で、人の指標が動いたのは 2026-04-23 の週だと分かった。ユーザーの指摘: 「なぜ人が動いたのか」と「Claude Code と Codex のどちらがいいか（結論が出せなければ比較）」まで無いと、読者は満足しない。

- 「なぜ」は、仮説ごとに「正しければ何が観測されるか」を先に書き、手元の issue の題名（3 リポジトリ全件、2026-09-21 取得）と Hacker News の題名で確かめる。因果は証明できない。整合するものと、しないものを分ける
- 「どちらがいいか」は**結論を出さない**。理由: (1) 下書き・集計を Claude Code（Anthropic 製）が担当しており、審判が当事者になる、(2) 出力の質は公開データでは測れない、(3) 機能・料金の比較は数週間で古くなる。代わりに、公開データで比べられる項目だけを表にし、比べられないものを明記する

## 定義

- データ: `data/proxies/2026-09-21/issues/*.jsonl`（作成者の `__typename` が Bot のものを除く）と `hn/*.json`。日は UTC、issue は createdAt
- 期間: **P0** = 2026-01-07〜03-03（56 日。Anthropic の公表文が言う影響期間の前）、**P1** = 2026-03-04〜04-20（48 日。影響期間）、**P2** = 2026-04-23〜05-27（35 日。人の指標が動いた週から 5 週）
- **割合** = 期間内の issue のうち、題名が規則に合うものの割合。**比** = 割合どうしの比
- 語の規則（題名、大文字小文字を区別しない、Python の `re.search`）:
  - **品質**: `quality|degrad|worse|dumb|lazy|nerf|hallucinat|forget|lobotom|stupid|less capable|intelligence|ignor\w* (instruction|claude\.md|rule)|not follow|doesn.?t follow`
  - **利用枠・料金**: `rate.?limit|usage limit|limit reached|hit\w* (the |my )?limit|quota|weekly limit|5.?hour|session limit|credit|billing|pricing|\bprice|subscription|overage|max plan|pro plan|plus plan|expensive|token usage|usage (spike|drain|burn)`
  - **相手への言及**: claude-code の題名では `codex|openai|chatgpt|gpt-?\d`、codex の題名では `claude|anthropic|\bopus\b|\bsonnet\b`
  - **`[MODEL]` 接頭辞**（claude-code だけ）: 題名の先頭（空白を除く）が `[MODEL]`。利用者が「Model Behavior Issue」のテンプレートを選んだ issue

## 予測と判定（値を見る前に凍結）

判定は共通: 比が **1.5 以上**なら支持、**1.2 未満**なら不支持、間は保留。分母の期間（P0）の該当が **20 件未満**なら判定不能。

|---|---|---|
| **R1a** | 品質への不満は、人が動く前に増えていた | claude-code の「品質」語の割合: P1 ÷ P0 |
| **R1m** | 同上（テンプレートで測る） | claude-code の `[MODEL]` 接頭辞の割合: P1 ÷ P0 |
| **R1b** | 利用枠・料金への不満は、人が動く前に増えていた | claude-code の「利用枠・料金」語の割合: P1 ÷ P0 |

## 利益相反の規律（0001・0003 に追加）

5. 語の規則は両方のリポジトリに同じものを当て、出た数字をそのまま書く。Anthropic に不利な結果（不満が増えていた、など）も有利な結果も、同じ節に同じ大きさで書く
6. 事後に、規則に合った題名を無作為に取り（乱数の種 20260922、区分 × 期間ごとに最大 40 件）、規則が意図した内容を拾えているか（適合率）を数えて併記する。数えるのは Claude なので、その旨を書く。適合率で判定は変えない
7. 「どちらがいいか」は書かない。書かない理由を記事に書く

### 見直しの規則

本決定のコミット以降、期間・閾値・語の規則・比較表の定義を変えない。実装上の細部は、集計を実行する前にスクリプトの冒頭に書いてコミットする。

## 既知の限界（結論に必ず添える）

1. issue の題名は、書いた人が選んだ言葉でしかない。語の規則は不満を取りこぼすし（英語以外、遠回しな表現）、関係ない題名も拾う（適合率は事後に数える）
2. issue は利用者のごく一部が書く。不満の割合が増えても、利用者全体の不満が増えたとは限らない。逆も同じ
3. 時期が重なっているだけで、因果は言えない。2026-04-23 には Anthropic の公表文・利用枠のリセットと OpenAI の GPT-5.5 が重なっており、どちらが効いたかは分けられない
4. `[MODEL]` 接頭辞は claude-code にしか無く、対照が取れない。codex 側の「モデルへの不満」は同じ物差しでは測れない
5. 「issue への対応」は運営の方針（自動で閉じるか、重複をどう扱うか）を映す指標で、製品の良し悪しではない
